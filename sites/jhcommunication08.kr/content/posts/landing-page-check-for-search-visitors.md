## 순위보다 도착 지점을 먼저 봅니다
사이트의 검색 노출을 관리할 때 순위 숫자에 먼저 눈이 가지만, 더 앞서 확인할 것은 검색한 사람이 어디에 도착하느냐입니다. 특정 서비스 이름을 검색했는데 관련 설명 없이 일반적인 회사 소개 화면만 나온다면 검색어와 페이지가 맞지 않는 것입니다.

그래서 점검은 "검색어 하나를 정하고, 그 검색어로 들어온 사람이 첫 화면에서 답을 얻는가"를 따라가는 방식으로 진행합니다. 이렇게 하면 어느 페이지를 고쳐야 하는지가 구체적으로 보입니다.

## 서비스별·질문별 문서가 있는지 확인합니다
현재 사이트에 서비스별 설명 문서와 질문별 안내가 따로 있는지부터 살핍니다. 대표 페이지는 주요 업무와 위치, 문의 방법을 보여 주고, 세부 페이지는 각 서비스의 범위와 이용 절차를 설명하는 구조가 이해하기 쉽습니다.

비용에 관한 질문은 어떤 항목이 포함되는지, 어떤 조건에서 달라지는지를 중심으로 정리합니다. 같은 내용을 제목만 바꿔 여러 문서에 반복하면 관리가 어려워지고 이용자는 차이를 알 수 없으므로, 중복된 문서는 합치거나 실제로 다른 질문을 담도록 고칩니다.

## 지역 표기는 실제 제공 범위에 맞춥니다
지역 이름을 쓸 때는 실제 사업장과 서비스 제공 범위에 맞춥니다. 여러 지명을 한꺼번에 넣어 방문할 수 있는 지점이 여러 곳인 것처럼 보이게 하는 것은 오해를 부릅니다.

서비스가 방문형인지, 찾아가는 형태인지, 온라인으로도 가능한지를 분명히 밝히고, 지도 서비스와 홈페이지에 적힌 주소와 운영시간이 같은지 확인합니다. 실제로 제공하지 않는 지역에서 들어온 문의를 성과처럼 부풀려 설명하지 않는 것도 신뢰를 지키는 방법입니다.

## 기술적으로 열리고 눌리는지 직접 시험합니다
주요 페이지가 정상적으로 열리는지, 모바일에서 메뉴와 버튼이 작동하는지, 삭제된 페이지로 이어지는 링크가 남아 있지 않은지를 직접 눌러 확인합니다. 화면에서 보이는 것과 실제로 동작하는 것은 다를 수 있습니다.

페이지 제목은 본문이 답하는 핵심 질문과 일치시키고, 첫 문단에서 곧바로 답을 제시합니다. 수정한 날짜와 이유를 기록해 두어야 나중에 유입이 달라졌을 때 어떤 변경 때문인지 비교할 수 있습니다.

## 외부 운영사에 맡길 때 확인할 것
광고나 콘텐츠 운영을 외부에 맡길 때는 게시 편수나 순위 약속보다 현재 사이트의 오류를 어떻게 찾고 누가 고치는지를 먼저 물어봅니다. 검색 결과의 특정 위치는 누구도 약속할 수 없지만, 이용자가 필요한 페이지에 도착하는지는 검증할 수 있습니다.

유입된 검색어와 실제 문의를 함께 보면서 빠진 설명을 채우는 운영이 필요합니다. 광고비를 늘리기 전에 문의 양식과 연락처가 정상 작동하는지부터 시험해 보는 것이 순서입니다.

## 보고서에 확인된 것과 아닌 것을 나눕니다
보고서에는 바뀐 페이지와 아직 검수하지 못한 정보를 분리해서 적습니다. 전문적인 사실을 다루는 업종이라면 운영자가 확인할 자료와 최종 책임자를 미리 정해 둡니다. 이렇게 하면 확인되지 않은 내용이 사실처럼 게시되는 일을 줄이고, 다음 점검에서 무엇을 이어서 살필지도 분명해집니다.

## 점검 주기를 정해 꾸준히 확인합니다
도착 페이지 점검은 한 번 하고 끝나는 작업이 아니므로 주기를 정해 반복하는 편이 좋습니다. 서비스 내용이나 운영시간, 연락처가 바뀐 시점마다 해당 페이지를 다시 열어 보고, 별다른 변경이 없더라도 정해진 간격으로 주요 페이지가 열리는지 확인합니다.

점검할 때는 담당자가 아닌 다른 사람이 처음 방문하는 입장에서 검색어를 입력해 보는 것이 도움이 됩니다. 내부 사람은 사이트 구조를 잘 알고 있어 불편함을 놓치기 쉽습니다. 발견한 문제는 고친 날짜와 함께 기록해 다음 점검 때 이어서 확인합니다.

점검에서 발견한 문제가 많더라도 한꺼번에 고치려 하지 않아도 됩니다. 이용자가 가장 자주 들어오는 페이지부터 순서를 정해 고치면 작은 노력으로도 검색 방문자의 경험이 눈에 띄게 나아집니다.

점검 결과를 팀과 공유할 때는 문제의 개수보다 이용자가 겪는 불편을 중심으로 설명하는 것이 좋습니다. 예를 들어 어떤 검색어로 들어와 어느 화면에서 멈추는지를 한 장면처럼 설명하면 담당자가 우선순위를 판단하기 쉽습니다. 기술 용어를 줄이고 이용자의 행동을 그대로 옮겨 적는 방식이 협업에 도움이 됩니다.
