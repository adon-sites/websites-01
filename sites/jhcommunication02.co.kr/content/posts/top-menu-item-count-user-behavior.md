## 정답 개수는 없고 도달 여부만 있습니다

사이트 메뉴가 많으면 모든 내용을 보여 주는 듯하지만 선택해야 할 항목이 늘어 오히려 찾기 어려워질 수 있습니다. 반대로 항목을 지나치게 묶으면 필요한 정보가 모호한 이름 뒤에 숨습니다. 그래서 "몇 개가 적당한가"라는 질문에는 고정된 숫자로 답하기 어렵습니다.

기준은 이용자가 원하는 일을 마치는 데 필요한 길이 분명한지입니다. 메뉴 하나하나가 어떤 과업으로 이어지는지, 눌렀을 때 기대한 화면이 열리는지를 따져 보는 것이 출발점입니다.

## 현재 메뉴를 한 문장씩 설명해 보기

현재 메뉴를 종이에 적고 각 항목을 눌렀을 때 기대되는 내용을 한 문장으로 써 봅니다. 서로 다른 두 메뉴가 같은 화면으로 이어진다면 중복일 가능성이 있고, 한 메뉴 안에 성격이 다른 정보가 섞여 있다면 이름만으로는 목적을 알 수 없습니다.

조직 내부의 부서 구분에 맞춰 만든 분류가 실제 이용자의 질문 순서와 다른 경우도 많습니다. 운영자에게는 자연스러운 이름이 처음 오는 사람에게는 낯설 수 있으므로, 이용자가 쓰는 표현으로 바꿀 수 있는지 살펴봅니다.

## 과업을 주고 어디를 누르는지 관찰하기

처음 방문하는 사람에게 구체적인 과업을 하나 주고 어디를 누르는지 지켜봅니다. 예를 들어 예약 변경 방법을 찾게 했는데 공지와 고객지원 사이를 계속 오간다면 두 메뉴의 경계를 다시 정해야 한다는 신호입니다.

클릭 수만 세지 말고, 잘못된 화면에 들어갔다가 되돌아온 경로를 기록합니다. 관찰 중에는 담당자가 옆에서 힌트를 주지 않아야 실제 사용 상황과 가까운 결과를 얻습니다.

## 모바일에서 같은 구조가 유지되는지 확인

컴퓨터에서 한 줄로 보이던 메뉴는 휴대전화에서는 접힌 목록이 됩니다. 항목이 많을수록 스크롤 위치, 하위 메뉴 펼침, 닫기 버튼 같은 요소가 행동에 영향을 줍니다. 화면을 확대했을 때 글자가 잘리거나 메뉴가 다른 버튼과 겹치지 않는지도 시험합니다.

항목 수를 줄였는데 꼭 필요한 메뉴가 아래로 밀려 눈에 띄지 않는다면 개선이라고 보기 어렵습니다. 모바일 화면에서 실제로 눌러 보는 점검을 변경 절차에 포함해 두세요.

## 바꿀 때는 연결된 주소와 문구를 함께 점검

메뉴 구조를 바꾸면 기존 주소와 외부에서 걸어 둔 링크가 영향을 받습니다. 이름만 바꾸고 상세 페이지 제목을 그대로 두면 이용자는 다른 내용을 열었다고 느낄 수 있습니다. 이동된 페이지에는 필요에 따라 이전 주소에서 새 위치로 이어지는 경로를 마련하고, 공지나 문서에서 예전 메뉴 이름으로 안내하고 있지는 않은지 확인합니다.

상단 메뉴는 자주 바꾸기보다 변경 이유와 결과를 기록하면서 다듬는 편이 좋습니다. 항목을 추가할 때는 무엇을 대신하고 어떤 질문을 해결하는지 먼저 설명할 수 있어야 합니다. 좋은 메뉴 개수는 보기 좋게 맞춘 숫자가 아니라, 이용자가 헤매지 않고 목적지에 도착하는 구조에서 나옵니다.

## 개선 효과는 이렇게 가늠합니다

메뉴를 바꾼 뒤에는 방문자가 목적 화면에 도달하기까지 걸리는 단계와 되돌아오는 비율을 비교해 볼 수 있습니다. 사이트 분석 도구가 있다면 메뉴 클릭 뒤 이탈하는 화면을 확인하고, 없다면 상담 담당자가 받은 "어디서 찾나요" 질문의 변화를 기록해도 충분합니다.

한 번의 변경으로 결론을 내리지 말고 몇 주 동안 같은 기준으로 관찰한 뒤 다음 조정을 결정합니다. 메뉴 이름을 이용자가 실제로 쓰는 말로 맞추는 작은 수정만으로도 헤매는 경로가 줄어드는 경우가 많습니다.

## 메뉴 이름을 고르는 작은 요령

이름은 짧을수록 좋다고 알려져 있지만, 짧은 단어가 모호하면 오히려 클릭을 망설이게 합니다. "서비스", "정보" 같은 포괄적인 이름은 안에 무엇이 있는지 알려 주지 못합니다. 이용자가 해결하려는 일을 드러내는 단어, 예를 들면 "예약 변경"이나 "이용 안내"처럼 행동이 보이는 표현이 더 잘 읽힙니다.

같은 의미를 서로 다른 이름으로 부르지 않는 것도 중요합니다. 상단에서는 "문의"라고 부르고 하단에서는 "고객센터"라고 부르면 같은 곳인지 다른 곳인지 이용자가 판단해야 합니다. 이름을 한 번 정했다면 안내문, 버튼, 알림 문구에서도 같은 표현을 쓰도록 맞춥니다.
